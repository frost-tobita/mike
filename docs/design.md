# 設計と今後の計画

## サービスの考え方

「SNSの投稿」ではなく **「SNSアカウント（発信者）」** を登録して検索するサービスです。
例: 「Instagramでフォロワー1万人以上の、関東の料理系の発信者」を探す。

対応SNSは **X / YouTube / Instagram / Threads / TikTok / Substack** の6つ。
検索画面の上にSNSごとの **インデックス（見出しタブ）🗂️** を並べ、タブを押すだけでそのSNSの発信者に切り替わる。各タブには今の条件で何人いるかを表示する。

投稿を集めないので、SNSから大量のデータを取ってくる必要がなく、費用と規約のリスクを小さく始められます。

## 全体の仕組み

```
 利用者 ──▶ 検索画面（WordPress） ──▶ 検索の窓口 ──▶ 検索エンジン部分
                                                     ├─ 今: MySQL（WordPressと同じデータベース）
                                                     └─ 将来: OpenSearch などに差し替え
 運営者 ──▶ 管理画面 / CSV取り込み ──▶ データベース
```

- **発信者** は WordPress の「投稿」の一種として保存する。紹介文や写真、個別ページ、SEO 対策など WordPress の機能をそのまま使える。
- **SNSアカウント** は専用の表（テーブル）に保存する。SNSの種類・フォロワー数で素早く絞り込めるよう索引を付けてある。
- **検索エンジン部分は差し替え式**。件数が増えたら、画面を作り直さずに検索の中身だけ高速なものへ交換できる。

## 速度の実測（開発環境）

ダミー発信者 20,000人・アカウント約40,000件で計測。

| 検索の内容 | かかった時間 |
|---|---|
| Instagram でフォロワー10万人以上 | 約 0.03秒 |
| 地域「関東」＋ジャンル「料理」 | 約 0.02秒 |
| 全員をフォロワー順に並べる | 約 0.1秒 |
| キーワード「料理」 | 約 0.1秒 |

数万人規模までは今の仕組みで十分速い。キーワード検索と全件並べ替えは人数に比例して遅くなるため、**10万人を超えるあたりで検索専用ソフトへの切り替え（フェーズ4）** を予定する。

## 今後の計画

### フェーズ1（完了）: 土台
登録・検索・発信者ページ・CSV一括登録・検索API。SNSごとのインデックス（タブ）。

### フェーズ2（完了）: 発信者本人による登録と審査
- 発信者がメールアドレスとパスワードで会員登録し、マイページから掲載内容を申請
- **新規登録も変更も、運営の審査を通ったものだけを公開**
  - 審査中も、前に承認された内容がそのまま公開され続ける（承認された時点で入れ替わる）
  - 審査待ちの申請は1人1件。審査中に送り直すと、申請の中身が新しい内容に置き換わる
  - 差し戻すときは理由が必須。発信者のマイページとメールに表示され、直して再申請できる
- 審査画面では、現在の掲載内容と申請内容を並べ、変わった項目を黄色で表示。SNSはリンクになっていて本人確認しやすい
- 他の発信者が掲載中のアカウントは登録できない（なりすまし・重複の防止）
- 掲載停止は審査なしで即時。再掲載は審査あり
- 発信者は WordPress の管理画面に入れない

#### まだ決めていない・今後の候補

- 利用規約・プライバシーポリシーのページ（登録画面からリンクする）

- 退会（アカウント削除）の手続き

### フェーズ2.5（完了）: 紹介リンクとおすすめ順
発信者に検索エンジンを広めてもらうため、発信者ごとに専用の紹介リンクを発行し、その流入を表示順位に反映する。

**紹介リンク**: `https://サイト/r/コード/`（コードは8文字・一度作ると変わらない）。アクセスすると流入を記録し、その発信者のページへ移動する。発信者はマイページでリンクをコピーでき、流入人数と順位を確認できる。

**流入の数え方（表示順位に影響するため厳しめ）**
- 同じ人の同じ日のアクセスは1回だけ数える
- 検索エンジンやSNSのリンク確認用ロボット、ブラウザの先読み、発信者本人のアクセスは数えない
- IPアドレスは保存しない。IP・ブラウザ・日付を混ぜた元に戻せない文字列だけを保存し、90日で消す

**おすすめ順（検索結果の初期の並び順）**

| 項目 | 内容 |
|---|---|
| ① 紹介流入点 | 直近30日の紹介流入人数の順位を0〜100点に換算 |
| ② フォロワー点 | 全SNSの合計フォロワー数の順位を0〜100点に換算 |
| 総合点 | （① × 1 ＋ ② × 1）÷ 2　※重みは管理画面で変更可 |

- 順位の換算: 1位が100点、最下位が0点、同じ数の人は同じ点（点 = 自分より少ない人の人数 ÷（全体の人数 − 1）× 100）
- 数そのものではなく順位を使う理由: フォロワー数は数百〜数百万と桁が違い、そのまま足すと①の効果が消えてしまうため
- 計算は1時間ごとに全員分をまとめて行う（2万人で約1秒）。検索は保存済みの点数で並べるだけなので速い
- 同点のときは合計フォロワー数の多い順

**運用上の注意**: 流入が0人の発信者が多いうちは、数人の流入でも①の点が大きく上がる（例: 流入5人で①89点）。リンクを使ってもらう動機づけには良いが、不正に増やそうとする人が出たら、期間や重みの調整、対策の追加を検討する。

### フェーズ2.6（完了）: 広告枠
収益化のため、広告を「控えめに、でも広告とはっきり分かるように」表示する。

| 枠 | 最初の設定 | 置き方 |
|---|---|---|
| トップページ：右上（四角・300×250） | オン | `[sns_ad slot="top_side"]` |
| トップページ：コンテンツの間（横長） | オン | `[sns_ad slot="top_infeed"]` |
| 検索結果：一覧の上 | オン | 自動 |
| 検索結果：一覧の途中（5人目のあと・1ページ1回） | オン | 自動 |
| 検索結果：一覧の下 | オフ | 自動 |

- 広告の種類: 画像＋リンク（クリック数も計測）／HTMLコード（アフィリエイト）／Googleアドセンス
- 1つの枠に出すのは1回の表示につき1つ。複数登録すると「表示の割合」に応じて入れ替わる。同じページで同じ広告は2回出さない
- すべての広告に「広告」ラベル（景品表示法のステルスマーケティング規制への対応。文字は変更可、空にはできない）
- 画像広告のリンクには `rel="sponsored nofollow"` を付ける（検索エンジンの決まり）
- スクリプトを含むコードを保存できるのはサイト管理者だけ
- 表示回数・クリック数は日ごとに集計（ロボットとサイト管理者は数えない）。HTML・アドセンスのクリック数は各社の管理画面で確認する
- `ads.txt` は管理画面から設定でき、`/ads.txt` で配信される
- 注意: ページを丸ごと保存して速くする「キャッシュ」を使うと、広告の入れ替わりと表示回数の計測が働かなくなる。キャッシュを入れるときは広告枠の扱いを見直す

### フェーズ2.8（完了）: 退会

- 本人に「退会が完了しました」、運営に「退会がありました」のメールを送る
- 規約ページのひな形（利用規約 第11条、プライバシーポリシー 8・10、利用上の注意事項）も、マイページから退会できる内容に合わせた

### フェーズ2.10（完了）: 発信者ページのハブ化と総合アルゴリズム
**発信者ページをハブ（拠点）にする**
- 6つのSNSに加えて「その他のリンク」（ブログ、企業サイト、ネットショップ、ほかのSNSなど）を5つまで。リンクには `rel="nofollow ugc"` を付ける（利用者が登録したリンクであることを検索エンジンに伝える）
- 発信者がマイページから記事を書ける（見出し・太字・リスト・引用・リンクが使える編集画面）。新しい記事も、公開中の記事の変更も運営の審査あり。変更の審査中は前の内容を表示し続け、差し戻された変更は消さずに直して出し直せる
- 記事の下には書いた人の紹介・SNS・リンク・同じ人の他の記事。発信者ページには記事一覧と「似ている発信者」

**計測（大規模でも記録が膨らまない作り）**
- ブラウザの小さなスクリプトが、表示・滞在時間・リンクのクリックを送る。ページ表示時に発行する合言葉（3時間有効）が無い記録は受け付けない
- 滞在時間は「画面に表示され、1分以内に操作があった時間」だけ。最大600秒
- 同じ人・同じ発信者・同じ日は1回だけ数える。ロボット（ヘッドレスブラウザを含む）、本人、運営は数えない。IPアドレスは保存しない
- 1人ごとの記録（重複防止用）は2日で削除し、「発信者×日」の合計だけを残す

**総合アルゴリズム（おすすめ順）**

| 信号 | 測るもの | 初期の重み |
|---|---|---|
| 紹介リンク | 紹介リンクから来た人数（最近ほど重く） | 25 |
| フォロワー | 全SNSの合計フォロワー数 | 25 |
| ページ閲覧 | 発信者ページと記事を見た人数（最近ほど重く） | 15 |
| 滞在時間 | ページを実際に見ていた時間の平均 | 15 |
| リンクのクリック率 | 見た人のうちSNSや外部リンクを押した割合 | 10 |
| 記事の活動 | 最近公開した記事の数（新しいほど重く） | 10 |
| サイトの利用日数 | 発信者がログインしてこのサイトを使った日数（最近ほど重く） | 5 |
| サイトの利用時間 | 発信者がログイン中にこのサイトを使っていた時間（1日30分まで、最近ほど重く） | 5 |
| 紹介ネットワーク | 招待して掲載された発信者と、その先の段（0.9.0で追加、下記） | 10 |
| お気に入り | ページを見てお気に入りに登録した人数（1.0.0で追加） | 5 |

- 各信号を全体の中での順位から0〜100点にし、重み付き平均を総合点にする（紹介:フォロワー = 1:1 は維持）
- 最近の動きほど重く数える（初期設定では14日前の動きを半分に）
- 平均値（滞在時間・クリック率）は、全体の平均に寄せて計算する（見た人が少ないと偶然に左右されるため）。まだ誰にも見られていない人は最下位扱い
- 不正の疑い: 「紹介リンクのクリックが20件以上あるのに、ページ表示がその2割未満」「閲覧30件以上なのに平均滞在5秒未満」は該当する点数を半分にし、管理画面の「要確認」に表示。計測を始めてしばらくは、計測前の紹介リンクとは比べない（正直な人が疑われないように）
- 計測のアドレスやファイル名には track などの言葉を使わない（広告ブロッカーに止められて、本物の閲覧が数えられなくなるのを防ぐ）
- 発信者自身のサイト利用（0.8.0で追加）: ログイン中の発信者が開いたページで、利用した日と「画面を見て操作していた時間」を記録。自分の順位に関わるため水増し対策として、1日30分まで・1日1回まで・1回に60秒まで・実際に経った時間まで、ログインした本人の記録のみ受け付ける
- 重み・期間・半分に数える日数は管理画面「発信者 → 表示順の設定」で変更できる
- 2万人で計算は約1.3秒。さらに大規模になったら、計算をデータベース側（集計関数）や検索専用ソフトに移す

**注意**: 始めたばかりで閲覧などのデータを持つ人が少ないうちは、少しの動きでも順位が大きく変わる。人数が増えるにつれて落ち着く。

### フェーズ2.11（完了）: note・Brain のリンクと発信者仲間の招待
**note・Brain**
- 発信者ページに「コンテンツ販売・ブログ」の欄。URLを貼ってもアカウント名だけを取り出して保存（審査あり）。SNSの一覧やフォロワー数には含めない
- ほかのサービスを足すときは `snscs_profile_stores` フィルター

**招待の流れ**
1. 発信者Aが招待リンク（`/join/コード/`）か紹介リンク（`/r/コード/`）を共有する
2. 来た人のブラウザに30日間、Aのコードを覚えておく（登録画面に「Aさんからの招待です」と表示し、招待コード欄に自動で入る）。口頭で伝えるときは招待コードを入力してもらう
3. 来た人Bが登録し、**審査を通って初めて掲載されたとき** にA→Bのつながりを確定（審査前・掲載停止中の人は数えない）。Aにはメールでお知らせ

**紹介ネットワークの点数**（新しい信号。初期の重み10）
- Aの値 = 段ごとに「(参加ボーナス10 ＋ その人の紹介リンク流入) × 減らし方^(段−1)」を合計
- 初期設定: 3段目まで、1段深くなるごとに50%。管理画面「表示順の設定」で1〜5段、減らし方、参加ボーナスを変更できる
- 不正の疑いがある人の紹介流入は数えない（参加ボーナスだけ）。つながりが輪になっていても止まる作り。計算量は「人数×段数」
- 3人以上招待した人には「アンバサダー」バッジ

**法律面の配慮**
- 何段にもわたる紹介に **お金・ポイントなどの報酬を付けると、連鎖販売取引（特定商取引法）や無限連鎖講（ねずみ講）とみなされるおそれ** がある。このため招待は表示順にだけ使い、報酬は出さない。利用規約（第7条の2）・プライバシーポリシー・利用上の注意事項にも明記した

### フェーズ2.12（完了）: 集客と回遊（1.0.0）
**一人ひとりに合わせたおすすめ（パーソナライズ）**
- 好みの記録はブラウザの中だけ（localStorage）。サーバーはクッキーに入った要約（ジャンル・SNS・地域の重み、最近見た・お気に入りの番号）を読むだけで、個人ごとに保存しない
- 育て方: 検索の条件（ジャンル+1、SNS+1、地域+0.5、キーワードに含まれるジャンル+0.7）、発信者ページ（ジャンル・SNS・地域。30秒を超えて見た時間に応じて追加、リンクを押すと+0.5）、記事・コラム（読んだ時間に応じて）、お気に入り（+2）。14日で半分に薄れる
- 近さ personal = 0.45×ジャンル + 0.2×SNS + 0.1×地域 + 0.25×一緒に見られている（それぞれ0〜1）
- おすすめ順 = (1 − 強さ) × 総合点 + 強さ × 100 × personal（強さは初期30%、「あなたへのおすすめ」は60%）。データベースの並び替えの式として計算するので、2万人でも約0.25秒
- 一緒に見られている発信者（協調フィルタリング）: 前日に同じ人が見た発信者の組を毎日数え（多く見る人の1件は 1/log2(1+件数) に軽く）、古い組は毎日5%ずつ薄める。予測 = Σ(起点の重み × 組の強さ) ÷ √閲覧数
- 見た発信者がまだ少ない人には「いま人気」を出す。理由（「料理をよく見ているあなたに」「○○を見た人に人気」）を添える
- ブラウザの GPC（追跡拒否）設定を尊重。検索結果で一人ひとりに合わせたときはお知らせを出し、ページをキャッシュさせない

**回遊**
- お気に入り・最近見た発信者（お気に入りページ、各ページの下）、人気・急上昇の検索キーワード（設定した人数以上が調べた言葉だけ、メールアドレスや長い数字は記録しない）
- 0件のときは条件を1つずつ外した場合の人数を示す。パンくず、関連する特集、サイト内ナビ
- 表示順位に「お気に入り」（重み5）を追加。その日にページを見た人の登録だけを数える

**集客**

### フェーズ2.14（完了）: 学習する検索アルゴリズム（1.4.0）
管理画面「発信者 → 検索アルゴリズム」で設定・確認する。

**1段目: 候補集め（自前の検索索引）**
- 発信者ごとに、名前・SNSのID・ジャンルと地域・タグ・紹介文・記事タイトルの6項目を「単語」に分けて索引（`snscs_idx_terms` / `snscs_idx_docs`）に入れる。日本語は2文字ずつ区切る（辞書が要らない）。全角・半角、ひらがな・カタカナ、大文字・小文字は自動でそろえる
- 関連度は BM25（検索エンジンの定番の式）。項目ごとに重み（名前3.0 〜 記事0.7）
- 言い換え辞書（インスタ＝instagram など。管理画面で編集）。どれか1つの書き方の単語がそろえば一致
- 登録・変更・記事の公開のたびに、その人の索引を作り直す。全員分は1時間ごとに少しずつ、または管理画面のボタンで
- 結果0件のときの「もしかして」（ジャンル・地域・人気キーワード・辞書・上位の発信者名から、いちばん近い言葉）と、入力中の候補（`/wp-json/snscs/v1/suggest`）

**2段目: 並べ替え**
- 最終点 = 関連度の割合 × 関連度 ＋ 残り × 総合点。検索の意図（人の名前 → 関連度85%以上、ジャンル・地域の名前 → 関連度を軽く）で割合を変える
- 1ページ目は、同じSNS・同じジャンルが続かないよう少しずつ点を引いて選ぶ（多様さ）。表示の少ない人を決まった枠に出す（お試し表示。トンプソン・サンプリング）

**学習のもと（記録）**
- 検索ごとにランダムな番号（qid）を作り、表示した人と順位を記録（`snscs_search_events`、30日で削除）。押した・満足（30秒以上見た、SNSへ進んだ）・すぐ戻った（15秒以内）をブラウザから送る
- 毎晩: 順位ごとのクリック率を出し、「その順位なら普通これくらい押される」に対して実際に何倍押されたか（検索でのクリック率）と、満足度を発信者ごとに出す（`snscs_creator_feedback`）

**総合点に足した信号**（このフェーズで5つ追加。1.5.0 で「このサイトでの反応」を足して合計16）: 検索でのクリック率、満足度、つながりの信頼度（招待と「一緒に見られている」のつながりで PageRank。運営が選んだ「信頼できる発信者」を起点にする）、プロフィールの充実度、更新の新しさ。紹介リンク・閲覧がふだんの中央値から極端に急増した人は「要確認」にして、その点を半分にする（記録が14日分たまってから）

**重みの学習**
- 「押されて満足された人」と「その上にあったのに押されなかった人」などの組から、どの信号を重くすれば利用者の選び方を当てられるかを学ぶ（ペアの順序を当てるロジスティック回帰）。5分の1は確認用に取っておく
- 確認用で、手の重みより1ポイント以上よく当てられたときだけ使う。手の重みと「反映度」の割合で混ぜる。関連度の割合は学習の結果にかかわらず30%以上
- 使い方: 手の重みだけ / 自動（おすすめ） / A/Bテスト（訪問者の半分だけ学習した重みで並べ、満足の割合を比べる）

**AIの自動タグ**（任意・有料）: 紹介文と記事から、Claude が検索用の細かいタグを付ける。Batches API（半額）で毎晩まとめて依頼し、1時間ごとに受け取る。紹介文が変わった人は付け直す

**規模の目安（開発環境・2万人）**: 索引の作成 約70秒（1時間ごとに分けて実行）、キーワード検索 0.1〜0.2秒、毎晩の集計・信頼度・学習は数秒

### フェーズ2.15（完了）: アルゴリズムハック対策（1.4.0）
管理画面「発信者 → 不正対策」。検索順位を不正に上げる行為を自動で見つけ、その発信者の点数に倍率を掛けて順位を下げる（`snscs_integrity`）。
- 総合点に倍率を掛ける（おすすめ順・ランキングなど全部に効く）。キーワード検索では、言葉との一致の点にも同じ倍率を掛ける
- 判定は点数の計算し直しのたび（毎日）。直れば自動で元に戻る。理由が複数なら掛け合わせ（下限 ×0.1）

| 判定 | 見つけ方 | 倍率 |
|---|---|---|
| 名前の詰め込み | 名前にジャンル・地域・辞書の言葉が3つ以上、【】の羅列、区切りの羅列、40文字超 | ×0.5 |
| 紹介文の詰め込み | 同じ言葉が6回以上かつ1割以上、ハッシュタグ15個以上、2文字の組の偏り | ×0.5 |
| 紹介文のコピー | 記号を除いてまったく同じ紹介文（60文字以上）。最初に掲載された人は対象外 | ×0.6 |
| クリックの水増し | 同じ人・同じ発信者・同じ日の2回目以降のクリックは学習に数えず（`snscs_click_seen`）、その数が15回以上かつ正規のクリック以上 | ×0.5 |
| 釣り | 検索で30回以上押され、満足5%未満・すぐ戻る60%以上 | ×0.7 |
| 招待の水増し | 招待して掲載された5人以上のうち8割以上が30日間だれにも見られていない | ×0.7 |
| 運営の手動指定 | 管理画面または発信者の編集画面 | ×0.2 |

- 運営は「問題なし（対象外）」「手動で下げる」「自動の判定に戻す」を選べる
- 発信者のマイページ「あなたの分析」に、順位を下げていることと直し方を表示（行動の水増しは理由を細かく出さない）
- 2万人のテストデータで、普通の発信者の誤判定は0人

- 本人が連携したアカウントを別の発信者が登録していたら、そちらから外して記録する（なりすまし対策）。同じSNSアカウントを2人の発信者が連携することはできない
- 1時間ごとに少しずつ更新（連携は20時間ごと、YouTube は1日1回、X は設定した間隔）。Instagram・Threads のトークンは期限の15日前に延長、TikTok は期限前に延長。取得できなければ「エラー」にしてマイページで連携し直しを促す
- 100人以上いたのに急に0になった場合は、取得の不具合とみなして反映しない
- トークンは AES-256-GCM で暗号化して保存（鍵は WordPress の秘密の値から）。管理画面にも秘密の値は表示しない（空のまま保存したら今の値を残す）
- 戻り先のURL: `/wp-json/snscs/v1/oauth/callback`（各SNSのアプリに登録する）。state は15分・1回だけ有効
- 各SNSの接続先は `endpoints()` にまとめ、`snscs_sync_endpoints` フィルターで変えられる。テストでは各SNSの代わりのサーバーで、許可の画面からの戻り・トークンの交換と延長・数の取得・失敗時の動きを確かめた（実際のSNSとの接続は、本番でアプリを作ってから確認が必要）
- 日ごとの推移（`snscs_follower_history`）から、発信者ページに「30日で +○」

#### 当初の計画（参考）
各SNSの **公式API** を使い、フォロワー数を定期的に自動更新する。

| SNS | 方法 | 費用・条件の目安 |
|---|---|---|
| X | X API | 有料（プランにより月額が大きく異なる） |
| YouTube | YouTube Data API | 無料枠あり。登録者数は誰のチャンネルでも取得可 |
| Instagram | Instagram Graph API | 本人が「ビジネス/クリエイター」アカウントで連携すれば取得可 |
| Threads | Threads API | 本人の連携で取得可 |
| TikTok | TikTok API | 審査あり。本人の連携で取得可 |
| Substack | 公式APIなし | 購読者数は非公開のことが多い。本人申告または手入力で運用 |

本人に「SNSでログイン（連携）」してもらう方式にすると、**本人確認（なりすまし防止）とフォロワー数の正確さ** を同時に満たせる。

### フェーズ3.5（完了・1.13.0）: 記事のおすすめアルゴリズム（Google × X × note）
`SNSCS_Feed`（候補集め・予測・並べ方・記録・記事の検索）と `SNSCS_Feed_Admin`（学習・管理画面「記事のおすすめ」）。
- **候補集め（X の考え方）**: フォロー中の発信者の記事（30日）・フォローしている人のリポスト（14日）／一緒に読まれた記事（自分が反応・読了した記事に反応した人を、重なりの大きさで似ている順に重み付け＝コサイン類似度。人気で少しだけ割る）／好みのジャンル（閲覧の傾向・反応した記事・フォローの書き手のジャンル）／話題／質の高い記事／新着。最大約400本
- **予測（ロジスティック回帰）**: 10の特徴（フォロー・好みの近さ・一緒に読まれた・質・クリック率・話題・新しさ・書き手の信頼・充実度・新しい書き手）から「最後まで読む確率」。質は note の考え方で、読了率（6割）と反応率（いいね1・ブックマーク1.5・リポスト3、4割）をデータの少ない記事は平均に寄せて出す。書き手の信頼は総合点（Google の権威性）。不正対策の倍率・既読0.15倍・「興味がない」の書き手0.3倍
- **並べ方**: 同じ書き手は2本目から0.6倍ずつ、同じジャンルは4本目から0.93倍ずつ。3・8・13番目は表示の少ない記事のお試し枠（読了率のベータ分布からくじ）。理由を表示
- **学習**: 表示した記録（30日）から毎晩、重みを確率的勾配降下法で直し、確認用の2割でAUCが0.01以上良く読了が30件以上のときだけ使う。手動（初期の重みだけ）にもできる。シミュレーション（2,000回の表示）で AUC 0.756 → 0.780、好みのジャンルの記事が20本中7本 → 12本
- **記録**: 表示・おすすめから開いた・閲覧・読了（40秒以上、または80%以上スクロールして15秒以上）。同じ人の同じ日は1回、ロボット・運営・書き手本人は数えない。学習用の記録はランダムな番号だけで30日、重複防止は2日
- **表示**: 「みんなの記事」の「おすすめ」（最初のタブ）、会員ページの「おすすめ」、記事の下の「次に読むおすすめ」（その記事に続けて読まれる記事・同じジャンル）、`[sns_for_you_articles]`。「興味がない」ボタン
- **記事の検索（Google の考え方）**: 検索結果の下に「○○の記事」。発信者の記事とコラムを BM25（題名3・ハッシュタグ2・本文1）で、関連度 ×（0.55 + 0.45 × 質）×（0.8 + 0.2 × 書き手の信頼）× 不正対策 × 新しさ
